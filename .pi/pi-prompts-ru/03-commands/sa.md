Обнови уведомление об уязвимости GitHub для публикации: $ARGUMENTS

Для всех операций GitHub используй `gh`. Не публикуй уведомление, не меняй его состояние и не запрашивай CVE, если пользователь явно не согласился или в Markdown-черновике прямо не указано `request_cve: true`.

GitHub не предоставляет комментарии и обсуждения уведомлений безопасности репозитория через документированную схему REST OpenAPI или публичную схему GraphQL. Ответ 404 с предполагаемого адреса, например `api.github.com/repos/.../security-advisories/<GHSA>/comments`, `.../timeline` или `.../events`, ожидаем и сам по себе не означает ошибку авторизации. Не используй браузерную сессию, cookies или извлечение cookies для получения комментариев к уведомлению. Вместо этого явно скажи пользователю, что комментарии не были включены и что он может вставить важные комментарии, если хочет их учесть.

## обработка входных данных

• Если `$ARGUMENTS` является URL уведомления безопасности GitHub, начни исследование и подготовку черновика.
• Если `$ARGUMENTS` является путём к существующему Markdown-черновику, прочитай его и примени к уведомлению.
• Если после этого промпта пользователь пишет «обнови», «примени», «всё хорошо» или подобное, считай это одобрением применения ранее записанного временного Markdown-черновика. Перед обновлением GitHub перечитай файл с диска.
• Если нужно применить черновик, но его путь неизвестен, спроси путь к Markdown-файлу.

## первоначальная работа с уведомлением

1. Разбери URL на `owner`, `repo` и идентификатор `GHSA`.
2. Получи уведомление:
   ```sh
   gh api repos/<owner>/<repo>/security-advisories/<GHSA>
   ```
   Прежде чем предлагать изменения, точно сохрани исходные severity, вектор CVSS и оценку CVSS в том виде, в котором они возвращены.
3. Не получай комментарии и обсуждение, если пользователь не вставил их в разговор:
   • Изучи JSON уведомления: ссылки, авторство, связанные задачи и PR, поля обсуждений.
   • Не полагайся на выдуманные адреса API `/comments`, `/timeline` или `/events`; они часто возвращают 404, потому что GitHub не предоставляет комментарии черновых уведомлений через публичный API.
   • Не используй браузерную сессию, cookies или извлечение cookies для получения комментариев.
   • Явно сообщи пользователю следующую фразу. В исходном шаблоне требуется точный английский литерал:
     ```text
     Advisory comments were not included because GitHub does not expose them through the public API. Paste any relevant comments if you want them considered.
     ```
     Смысл: комментарии к уведомлению не включены, потому что GitHub не открывает их через публичный API; вставьте важные комментарии, если их нужно учесть.
   • Если пользователь вставил комментарии, прочитай и учти их.
   • Никогда не притворяйся, что комментарии прочитаны.
4. Проведи независимое исследование:
   • Прочитай текст уведомления, метаданные, затронутые пакеты, диапазоны версий, CVSS, CWE, ссылки, связанные задачи, PR и коммиты.
   • Изучи относящуюся к вопросу историю кода, релизы, журналы изменений, метаданные пакетов и теги.
   • Определи, исправлена ли уже уязвимость.
   • Если исправлена, найди исправленные версии и корректный диапазон уязвимых версий.
   • Не доверяй анализу автора сообщения без проверки.
5. Перед окончательным черновиком обсуди CVSS с пользователем:
   • Предложи вектор CVSS, оценку и серьёзность.
   • Кратко объясни спорные метрики.
   • Попроси подтвердить или поправить.
6. Спроси, нужно ли запросить CVE у GitHub для этого уведомления.
7. Запиши готовый к публикации Markdown-черновик в `/tmp`, например `/tmp/sa-<GHSA>.md`. Включи исходные CVSS из уведомления и предложенные или подтверждённые обновлённые CVSS.
8. Сообщи пользователю:
   • путь временного Markdown-файла;
   • исходный URL уведомления;
   • что он может изменить файл, затем написать «обнови» или передать путь.

## формат Markdown-черновика

Файл должен содержать YAML frontmatter, затем текст уведомления. Включи все поля, нужные для обновления GitHub и решения о запросе CVE.

Ниже сохранены имена машинных полей, литералы и обязательные названия разделов. Переведены пояснения заполнителей:

```markdown
---
advisory_url: https://github.com/<owner>/<repo>/security/advisories/<GHSA>
owner: <owner>
repo: <repo>
ghsa_id: <GHSA>
summary: <краткое описание уведомления>
original_severity: <low|medium|high|critical|null>
original_cvss_vector: <исходный CVSS:3.1/... или null>
original_cvss_score: <исходное число или null>
severity: <предложенное/подтверждённое low|medium|high|critical>
cvss_vector: <предложенный/подтверждённый CVSS:3.1/...>
cvss_score: <предложенное/подтверждённое число>
cwe_ids:
  - CWE-...
vulnerabilities:
  - package:
      ecosystem: npm
      name: <package-name>
    vulnerable_version_range: <диапазон>
    patched_versions: <диапазон-или-версия>
request_cve: false
---

# <Заголовок уведомления>

<Краткое описание уязвимости и уязвимого поведения.>

## Info

<Техническое объяснение первопричины и затронутого компонента. Сосредоточься на фактах, нужных защитникам и сопровождающим. Не включай шаги PoC, полезные нагрузки эксплуатации и готовые строки для эксплуатации.>

## Impact

<Кто может воспользоваться уязвимостью, необходимые условия, влияние на конфиденциальность, целостность и доступность, реалистичные условия развёртывания.>

## Affected versions

- Affected: `<диапазон>`
- Patched: `<версия или диапазон>`

## The solution

<Описание исправления и исправленного релиза.>

## Recommendations

<Рекомендации по обновлению и эксплуатационным мерам защиты.>

## Workarounds

<Обходные меры, если есть; иначе целиком убери раздел.>

## Timeline

- YYYY-MM-DD: Получено сообщение
- YYYY-MM-DD: Исправление закоммичено
- YYYY-MM-DD: Выпущена исправленная версия
- YYYY-MM-DD: Опубликовано уведомление

## Credits

<Указание автора сообщения или исследователя, если уместно; иначе убери раздел.>

## References

- <ссылки на релизы, коммиты, уведомления, документацию>
```

Ориентируйся на стиль уведомлений curl: ясные разделы, прямой язык, факты о затронутых и исправленных версиях, рекомендации, хронология и авторство. Не включай PoC.

## применение черновика к GitHub

Когда пользователь одобряет словами «обнови» или подобными либо даёт Markdown-путь:

1. Перечитай Markdown-файл с диска. Не полагайся на ранее сгенерированный текст в памяти.
2. Разбери YAML frontmatter и основной текст.
3. Составь JSON во временном файле. Соответствие полей:
   • `summary` из frontmatter;
   • `description` из Markdown-текста после frontmatter;
   • `severity` из frontmatter, если есть;
   • `cvss_vector_string` из `cvss_vector`;
   • `cwe_ids` из frontmatter;
   • `vulnerabilities` из frontmatter;
   • не отправляй `original_severity`, `original_cvss_vector` и `original_cvss_score`: они сохраняются только для истории проверки.
4. Обнови уведомление:
   ```sh
   gh api -X PATCH repos/<owner>/<repo>/security-advisories/<GHSA> --input /tmp/<payload>.json
   ```
5. Тогда и только тогда, когда frontmatter содержит `request_cve: true`, запроси CVE:
   ```sh
   gh api -X POST repos/<owner>/<repo>/security-advisories/<GHSA>/cve
   ```
   Сообщения «уже запрошен» и «уже назначен» не считаются фатальными; сообщи о них.
6. Сообщи, что обновлено:
   • URL уведомления;
   • краткое описание;
   • затронутый диапазон;
   • исправленные версии;
   • исходный вектор, оценка и серьёзность CVSS;
   • обновлённый вектор, оценка и серьёзность CVSS;
   • запрашивался ли CVE.

## правила безопасности

• Не включай PoC в итоговый текст уведомления.
• Не запрашивай CVE без `request_cve: true` в Markdown-файле.
• Не публикуй уведомление и не меняй состояние без явной просьбы пользователя.
• Не получай комментарии через браузерные сессии или cookies. Сообщи, что комментарии не включены, и предложи пользователю вставить нужные.
• Если есть неопределённость в затронутых диапазонах, исправленных версиях, CVSS или состоянии запроса CVE, спроси пользователя перед применением.
