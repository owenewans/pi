# Выпуск pi

Выполняйте команды репозитория из его корня (на два каталога выше исходного файла этого навыка), если не указано иное.

**Синхронное версионирование**: у всех пакетов одна версия; каждый релиз обновляет их вместе. `patch` = исправления + дополнения, `minor` = несовместимые изменения. Мажорных релизов нет.

1. **Обновите CHANGELOG**: спросите пользователя, запускал ли он промпт `/cl` на последнем коммите `main`. Если нет, он должен сначала запустить `/cl`, чтобы проверить и обновить раздел `[Unreleased]` каждого пакета перед релизом.

2. **Локальный дымовой тест**: соберите неопубликованный релиз и проведите дымовой тест вне репозитория (чтобы он не мог находить файлы рабочего пространства):
   ```bash
   npm run release:local -- --out /tmp/pi-local-release --force
   cd /tmp

   # Node package install smoke tests
   /tmp/pi-local-release/node/pi --help
   /tmp/pi-local-release/node/pi --version
   /tmp/pi-local-release/node/pi --list-models
   /tmp/pi-local-release/node/pi -p "Say exactly: ok"
   /tmp/pi-local-release/node/pi

   # Bun binary smoke tests
   /tmp/pi-local-release/bun/pi --help
   /tmp/pi-local-release/bun/pi --version
   /tmp/pi-local-release/bun/pi --list-models
   /tmp/pi-local-release/bun/pi -p "Say exactly: ok"
   /tmp/pi-local-release/bun/pi
   ```
   Смысл комментариев сохранённого примера: `Node package install smoke tests` означает «дымовые тесты установленного пакета Node», `Bun binary smoke tests` означает «дымовые тесты исполняемого файла Bun». Литерал промпта `Say exactly: ok` сохранён без изменений и означает «скажи в точности: ok»; `ok` является требуемым литералом ответа.

   Проверьте запуск Node и Bun, вывод списка моделей и учётных записей, запуск интерактивного режима и хотя бы один настоящий промпт с предполагаемым поставщиком по умолчанию. Команды `/tmp/pi-local-release/node/pi` и `/tmp/pi-local-release/bun/pi` без аргументов запускают интерактивный режим; выполните каждую в tmux, отправьте промпт и дождитесь ответа модели, прежде чем считать интерактивный дымовой тест пройденным. Сбои блокируют релиз, если пользователь явно не принимает риск.

   Загрузите [interactive-testing.md](../02-project-skills/interactive-testing.md) и следуйте описанному процессу tmux. Запускайте каждый исполняемый файл релиза из `/tmp`, а не из корня репозитория.

3. **Запустите скрипт релиза**:
   ```bash
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:patch    # fixes + additions
   PI_ALLOW_LOCKFILE_CHANGE=1 npm_config_min_release_age=0 npm run release:minor    # breaking changes
   ```
   Смысл комментариев сохранённого примера: `fixes + additions` означает «исправления + дополнения»; `breaking changes` означает «несовместимые изменения».

   Если набор тестов уже прошёл в `npm run release:local` и падает только из-за нагрузки на машину, `PI_RELEASE_SKIP_TESTS=1` пропускает `./test.sh` в скрипте релиза; проверки и проверка установки упакованного пакета всё равно выполняются. Используйте это только с одобрения пользователя.

   Используйте `npm_config_min_release_age=0` только для команды релиза. Иначе обычное ограничение npm по возрасту пакетов в репозитории может блокировать обновление файла фиксации зависимостей релиза, когда текущая версия пакета рабочего пространства опубликована недавно. Перед отправкой просмотрите все изменения файла фиксации зависимостей или блокировки установки, созданные релизом.

   Скрипт релиза фиксирует новейший опубликованный каталог моделей для Nix (`nix/model-catalog.json`) и собирает рабочую копию с ним так же, как сборка Nix (он завершается ошибкой, если этот каталог старше изменений моделей в main; сначала опубликуйте каталог), повышает версии всех пакетов, обновляет журналы изменений, повторно генерирует артефакты релиза, выполняет `npm run check`, создаёт коммит `Release vX.Y.Z`, тег `vX.Y.Z`, добавляет новые разделы `## [Unreleased]` в журналы изменений, создаёт коммит `Add [Unreleased] section for next cycle`, затем отправляет `main` и тег. Не запускайте скрипт релиза повторно после отправки тега.

   Обязательные литералы сообщений коммитов: `Release vX.Y.Z` означает «релиз vX.Y.Z», `Add [Unreleased] section for next cycle` означает «добавить раздел [Unreleased] для следующего цикла».

4. **CI проверяет и объявляет релиз npm**: отправка тега `vX.Y.Z` запускает `.github/workflows/build-binaries.yml`. Задание `publish-npm` использует доверенную публикацию npm через GitHub Actions OIDC с окружением `npm-publish`; локальные `npm publish`, `npm whoami`, OTP или процесс WebAuthn не требуются. После публикации `announce-pi-dev-release` проверяет, что каждый публичный пакет рабочего пространства разрешается в точную версию релиза и что его архив npm доступен, затем записывает проверенный маркер релиза в R2. `pi.dev/api/latest-version` читает этот маркер; он никогда не должен объявлять релиз из npm до успешного завершения этого задания.

5. **CI собирает релиз Nix**: отправка тега также запускает `.github/workflows/nix.yml`, который собирает flake с этим тегом в Linux и macOS, затем перемещает ветку `stable` вперёд до коммита релиза. `nix run github:earendil-works/pi/stable` запускает последний релиз. Если сборка Nix завершается ошибкой, `stable` остаётся на предыдущем релизе; исправить тег нельзя, поэтому исправьте `main` и включите исправление в следующий релиз.

6. **Если публикация или объявление в CI завершились ошибкой**: изучите неуспешное задание. Вспомогательный скрипт публикации идемпотентен и пропускает версии пакетов, уже присутствующие в npm; задание объявления повторно проверяет доступность перед обновлением маркера R2. После исправления CI или временных проблем npm повторно запустите неуспешное задание или рабочий процесс. Не запускайте `npm run release:patch` или `npm run release:minor` повторно для той же версии.
